# AGENTS.md – notes for AI assistants working on this project

## What this is

"Слънце" (project/package name `ilios`): a small Kotlin web app that stores Open-Meteo weather for the user's places and shows it as charts, plus an estimate of solar production against a battery. The UI, advice texts, error messages and emails are **Bulgarian only** (dates `дд.ММ.гггг`, decimal comma). There is no language switch.

Guiding principle from the owner: **favour simplicity, speed and size over features.** Prefer no new dependencies, no build step for the frontend, no frameworks. Ask before adding libraries.

Stack (fixed by the owner): Kotlin, Ktor (CIO engine), Koin, Exposed, kotlinx.serialization/coroutines, embedded H2. Versions are in `build.gradle.kts` (Kotlin 2.4.x, Ktor 3.6, Exposed 1.5, Koin 4.2, JDK 25 in use). Angus Mail is used for SMTP. Logging is kotlin-logging (`KotlinLogging.logger {}`, a `private val log` per file) over SLF4J and logback (`logback.xml`); see Logging below.

## Run, build, test

```bash
./gradlew run                 # http://localhost:8081
./gradlew installDist         # build/install/ilios/bin/ilios
./gradlew buildFatJar         # build/libs/ilios-all.jar
./gradlew test                # in-process tests, throwaway database, no port, no network
./gradlew check               # tests + ktlint + detekt
./gradlew ktlintFormat        # fix formatting (rules in .editorconfig)
./gradlew detekt              # static analysis, ALL rules on (allRules); exceptions are explicit in config/detekt.yml or @Suppress; no baseline, keep it clean
# line length is 120 (ktlint and detekt); no magic numbers: shared units are in Units.kt
```

- Configuration is by environment variables: optional `SOLAX_URL` (SolaX region host), optional `BASE_URL` (reset-link address, default http://localhost:$PORT), optional `MAIL_HOST` (default smtp.gmail.com) and `MAIL_PORT` (default 587), optional `PORT` (default 8081; invalid values fail at start-up, see `portFrom` in `Config.kt`) and the mail pair: `MAIL_USERNAME` (the sending Gmail address) and `MAIL_PASSWORD` (its Google app password). There is no default account. If either is missing no mail is sent and reset links are printed to the server log (`PASSWORD RESET for …`).
- Everything else is deliberately hard-coded: DB `./data/ilios`, public Open-Meteo endpoints, `BASE_URL` defaults to `http://localhost:$PORT` (reset links), session cookie `Secure` + HSTS only when `BASE_URL` is https (`HTTPS` in `Config.kt`); all responses carry nosniff, frame-deny and no-referrer headers. These are in `Main.kt`, `Config.kt`, `weather/WeatherService.kt`, `auth/Mail.kt`. Changing any of them to be configurable is a product decision – ask first.
- The owner often has the app running locally on 8081 with their real data in `./data/`. **Never send test requests to 8081 and never `kill`/`pkill` by `MainKt`** – that kills the owner's instance and curl calls would hit their real database. For manual checks run a separate instance from a scratch directory on another port, e.g. `cd /tmp/scratch && PORT=18080 /path/to/build/install/ilios/bin/ilios`, and stop it by its PID. Automated checks: `./gradlew test`.
- Deploying on the server: `scripts/install` once, `scripts/update` for every later deploy (pulls, builds, copies to `/opt/ilios/app`, restarts; the database is never touched). The systemd units are template files in `deploy/systemd/` (`ilios.service`, `ilios-restart.service`, `ilios-restart.timer`, with `@APP_USER@`, `@INSTALL_DIR@` and `@CONF_DIR@` as placeholders); `update` (which `install` runs at its end) fills them in after the pull and installs each unit only when its text differs, reloads systemd when one changed and keeps the timer enabled. In `ilios.service` `Environment="JAVA_OPTS=..."` must be quoted (unquoted, systemd split it at the space and dropped `-Xmx512m`, so the heap cap never applied until 2026-11-08; the cap is now 256 MB: the live heap measured on prod after a full GC was 17.6 MB, the JVM's resident size about 200 MB) and `SuccessExitStatus=143` marks the JVM's exit on SIGTERM as a normal stop. The timer restarts the service on the 1st of January, April, July and October at 16:00 Europe/Sofia, so the H2 file is compacted at least that often (see Gotchas). The unit step of `update` has only been syntax-checked and its rendered text compared with the units on the server; it had not been run when it was written.

## Data model (Exposed, H2)

- `users(id, email unique, pass_hash)`; `tokens(hash, user_id, kind session|reset, expires)`.
- `locations(id, user_id, name, country, lat, lon, tz, position, solar, supplier, reserved_pct, allow_control, max_charge_w, charge_eff_measured)` – **solar settings are per place**; `position` is the per-user place order (edited by `PUT /api/locations/order` from settings). New places start with `solar = false`, `allow_control = false` (Разреши управлене: the inverter may be programmed) and `max_charge_w = 2000` (cap of the programmed grid charging, 500-6000 W, shown and edited in kW in settings; the reserved battery and this cap are shown only under the management toggle). `charge_eff_measured` (the share of the charging power that ends up stored in the battery, **not a setting**: the old `charge_eff_pct` override column is dropped at start-up) is the automatic value (see below), shown in settings as a label only (Ефективност на зареждане: измерена: N %, or the default until there is one); the default 85 % (`DEFAULT_CHARGE_EFF_PCT`) applies until a measurement exists. `Loc.chargeEfficiency` = measured ?: default. It scales the charge time, the planned-charge estimate and the euro figures. Panel power (kWp) and battery capacity (kWh) are **not** settings: they are read from SolaX and stored in `solax.pv_kwp` / `solax.battery_device_kwh`.
- `daily(location_id, day, t_max, t_min, rain_mm, radiation_mj, fetched_at)` – 14 past + 14 future days (past days are stored once and never replaced). `geocode_cache(query, json, fetched_at)` – place-search results. `discharge_days(location_id, day, t, discharge_w, load_w, grid_w, soc, charge_w)` – 5-minute battery discharge, home consumption and grid power (W), battery charge (%) and charging power (W) of the finished days since the Monday of last week (`dischargeHistoryIfDue`, 3 days per pass; SolaX reports no consumption, so `load_w` = panel power − battery charging power + grid import, with grid import = −`gridPower` of the inverter history (negative while importing); the discharge profile uses only the last 7 days).
- `solax(location_id, client_id, client_secret, plant_id, plants, plant_name, business_type, pv_kwp, produced_through, battery_days_through, battery_device_kwh, diag_devices, history_try_at, plant_read_at, inverter_sns, soc, battery_remaining_kwh, battery_power_w, battery_read_at, battery_try_at, battery_status, token, token_expires, status, due_at)` – one row per connected place; `produced(location_id, day, kwh, ac_kwh, load_kwh, bad)` – daily production from SolaX (`kwh` = `pvGeneration`, the panels' output, used for the chart and efficiency; `ac_kwh` = `inverterACOutputEnergy`, the SolaX app's "Inverter Output", only shown in the tooltip so numbers can be compared with the SolaX UI; `load_kwh` = daily home consumption from SolaX when reported). Both cascade with the place. **Bad cloud data:** SolaX once returned `pvGeneration` 4383 kWh for a 9 kWp plant (21.10.2026; the other fields of that day were normal); a day above kWp × 24 is stored with `produced.bad = true`, left out of `produced()` (so the estimate shows and the calibration ignores it), reported as `DayPoint.badCloud` and marked with a red "!" and a tooltip line on the weekly chart.
- `solar_today(location_id, day, t, soc, pv_w, bat_w, grid_w)` – 5-minute battery/inverter history for today (yesterday's rows are kept too).
- `night_plans(location_id, day, found_at, checked_at, day_start_kwh, solar_kwh, total_kwh, target_soc, sun_at, stop_by, soc_now, reached, charge_until, control, charge_from)` – the plan for one coming day zone, kept 14 days; `charge_until` = when the running charge ends, `charge_from` = the latest moment the charge can start and still end in time (both drive the 5-minute battery readings); `control` = outcome text of the last command. The old `rule_id`/`rule_soc` columns stay in existing databases, unused.
- `intraday(location_id, day, t, temp, rain_mm, event, radiation_wm2)` – 15-minute steps for 3 days.
- Foreign keys cascade on delete: deleting a place deletes its weather rows, deleting a user deletes places and tokens. (Covered by a test.)

## How weather works (important)

- **Pages read only from the database.** `WeatherService.days()` / `intraday()` never call the network.
- Only `WeatherService.refresh(loc)` talks to Open-Meteo: daily (`past_days=14`, `forecast_days=14`) and `minutely_15` (finest resolution; interpolated from hourly outside Open-Meteo's high-resolution regions).
- It is triggered when a place is added, and by `refreshLoop()` (launched in `Application.module()`), which checks every 10 minutes and refetches a place whose daily data is older than 1 hour **or** that has no intraday rows for today.
- Daily rows before today are kept as first stored; today and future rows are replaced. Intraday rows are replaced wholesale.
- A place with no data shows a "loading" card; an old but present dataset is kept if a refresh fails.

## SolaX Cloud (produced energy)

- Code split: `SolaxService` holds the lock and delegates the syncing to small collaborators that talk to SolaX through `SolaxSession`; the stateless database side is `SolaxRepository` (`plant`, `infos`, `update`), `SolaxConnection` (`configure`) and `SolaxReadings` (`produced`, `today`, ...), which routes, the report and tests call directly.
- **API details live in [`solax-api.md`](solax-api.md)** (auth, the endpoints used, response codes, enumerations, open questions). Read it before changing the `solax` package; update it when you learn something new about the API.
- Flow in short: token (cached) → all plants of the account (`page_plant_info`, paged, both business types tried; stored as JSON in `solax.plants` for the settings **dropdown**; **the first plant is selected by default**, `solax.plant_id` holds the selection) → the selected plant's record carries `pvCapacity` kWp and `batteryCapacity` kWh (read on first connect and then weekly via `plant_read_at`, or again when credentials or the selected plant change, to save quota) → one `get_stat_data` call per month involved in the not-yet-fetched days → `pvGeneration` per day stored in `produced`.
- Battery charge has **its own schedule, separate from production sync: every hour by day, every 30 minutes in the night zone, every 5 minutes in the 30 minutes before the night charge's latest start and end** (cached in the DB, `batterySlot`), plus one reading right after connecting. `readBatteryIfDue()` (called by `batteryLoop`, which checks every 5 minutes, and after saving credentials) reads when the last reading is older than the current slot and retries failures at most hourly (`battery_try_at`, cleared by every successful reading); the outcome text is `battery_status`. It lists the inverter serials once (`page_device_info`, cached in `inverter_sns`), then `realtime_data` with `deviceType=2&requestSnType=1` returns `batterySOC`, `batteryRemainings`, `chargeDischargePower`; the app stores the average %, summed kWh and power with the reading time. Plants without a battery capacity are never asked. The UI shows a chip and a gauge and always shows when the reading was taken.
- **Estimate for the rest of today (`report/Estimate.kt`):** 5-minute steps from now to midnight: the mean consumption per slot of the last 7 days (`discharge_days.load_w`), scaled by today's `loadEst` over those days' mean total (weather), against the 15-minute panel forecast; the sun serves the house first, the surplus charges the battery, a shortfall drains it to the place's **reserved battery** (`locations.reserved_pct`, 0-50 %, default 0, set in the SolaX Cloud section; SolaX does not expose it) and then comes from the grid. `report.estimate` feeds the dashed charge line, the pale grid-draw bars and today's ⚡ (`chargeNeeded`: peak charge under 99 % or the floor is hit). Needs consumption data from SolaX; without it the old discharge-mean estimate is used.
- **Night plan (`report/NightPlanner.kt`, `night_plans`):** the night zone is 22:00-06:00 in winter and 23:00-07:00 in summer time (`nightZone`). During it the battery is read every 30 minutes, and every 5 minutes in the 30 minutes before the charge's latest start (`night_plans.charge_from`, set by `NightPlanner.check` from `InverterControl.latestStart`) and before its end (`charge_until`) (`batterySlot`, `SolaxRepository.chargeTimes`; hourly outside the night zone). `SolaxService.batteryLoop` checks every 5 minutes (the sync loop keeps its 10 minutes), the planner loop every 5 minutes. A successful reading clears the `battery_try_at` gate (it used to hold the next reading back for an hour, so night readings were hourly); only failures back off. `NightPlanner.check()` (loop every 10 minutes) works out `compensation()` for the coming day zone when the fresh reading is at or below the reserved battery + 1 %, and refreshes the plan at each later check until the day zone starts: day start energy (net consumption from the day zone's start until the sun can power the house, `sunAt`) + solar compensation (the later shortfall until the night zone) = total; above the usable capacity the target is a full battery. Otherwise the target is `reserved% + total ÷ battery kWh × 100` (`compensation`, `nightTargetSoc`), so a good solar forecast legitimately gives a target well below 100 % (e.g. 80 %): charging to 100 % is not a goal. With **Разреши управлене** on, `controlInverter` also drives the inverter: while charging is needed (`!reached`, level above the reserved battery) `SolaxService.startCharge` sends SolaX remote mode **Push Power** (`batteryPower` = -`locations.max_charge_w`, `nextMotion` 160) with a timer that runs **until 5 minutes before the day zone start** (`CHARGE_END_BEFORE_MS`): only the start is calculated, as the latest start = that end minus the time needed (missing energy ÷ (`max_charge_w` × efficiency), longer by the stops of past nights (`ChargeStops`) + 60 s); the target is the computed level plus the expected consumption of those last 5 minutes (up to 100 %); the first command is held back while the next battery reading (5 minutes, the fast window) is still in time to finish by then, so the **last 5-minute reading before the latest start** starts it (a reading after it starts late, with a shorter timer); charging earlier would be drained by the house again, the command is **sent once** (no re-send while it runs: a new command replaces the running one and briefly leaves the mode, which showed as one-slot dips with grid 0 at the 30-minute readings; only a failed send is retried at the next reading), and `stopCharge` (`exit_vpp_mode`) ends it as soon as the plan is reached or management is switched off. The time the inverter charges until and an outcome text are kept in `night_plans.charge_until/control`. Failures are stored in `control` and retried at the next battery reading (30 minutes at night). API details and what is still unverified: `solax-api.md`. The plan also feeds the callout on the weekly chart, the Recommendations section and the ⚡ (shown for a planned day when `totalKwh > 0`). Days without a plan keep the daily forecast rule.
- **Battery history for the ⚡ icons (past days):** `batteryHistoryIfDue()` fetches, for each past day once, the battery history (`history_data`, `deviceType=2&requestSnType=1`, `timeInterval=30`, **at most 12 hours per request**, so two windows per day and three on the 25-hour day when summer time ends) and stores the day's highest charge (several batteries averaged per moment) in `battery_days(location_id, day, max_soc)`; `battery_days_through` is the progress marker, a backlog is worked off **one day per loop pass** (every 10 minutes) to stay under the rate limit, failures retry hourly (`history_try_at`). The chart shows ✓ for a past day when `max_soc ≥ 99`, ✗ otherwise; today/future/no history yet use the production-vs-capacity logic (tooltip says "по оценка" for past days).
- **Battery capacity** is the battery devices' summed `ratedCapacity` from `page_device_info?deviceType=2` (`solax.battery_device_kwh`, Wh for residential, read with the weekly plant record; `SolaxPlant.batteryKwh`, shown in the settings status line). When the device list gives no capacity the raw answer is kept in `solax.diag_devices` (no credentials in it) to inspect the real field names, and the place has no battery capacity (no battery section, no estimate). The plant record's own `batteryCapacity` is not used: it was too low on the owner's account (5.8 kWh for a battery sold as 15 kWh).
- A solar place with no synced plant yet has no battery section and no estimate (`report.solar = true`, `battery = null`); a plant without a battery gets the chart without the capacity line and ⚡ icons.
- API calls are limited and nothing is polled on page loads. **Refresh schedule (owner's rules):** weather and the solar forecast every hour (Open-Meteo; the forecast kWh is computed at report time from the stored radiation); **produced energy of past days is fetched once per day** (`produced_through` = last fetched day; on connecting it backfills from last week's Monday, then each new final day, yesterday after 02:00 local via `lastProductionDay`; days SolaX has no data for are never re-asked; today is not fetched); **battery charge hourly by day, every 30 minutes at night, every 5 minutes around the night charge's latest start and end**; panel power/battery capacity on connect then weekly. `syncLoop()` checks every 10 minutes (`syncIfDue` and the history passes), `batteryLoop()` every 5 minutes (`readBatteryIfDue`); `due_at` is only the 1-hour retry gate after a failure. Saving a place's credentials triggers an immediate `sync()` and battery read.
- Region host: env `SOLAX_URL` (default EU). The secret is stored in plain text in the database (needed for the API) and is **never** returned by the API or logged; keep it that way (status texts must not contain credentials).
- Each place keeps its own credentials, the selected plant (new credentials reset it to the first plant of the new account; a stale selection sent with new credentials is ignored) and a user-visible `status` string (it also reports the panel power and battery capacity SolaX returned).
- The power chart draws solid bars for measured past days and pale bars for estimates and forecasts (including today). `produced` is `null` in the report when not connected.
- Tests use Ktor's mock engine (`Solax*Test.kt`); never call the real SolaX API or send real credentials from tests. The only inverter **control** is the night charge in SolaX remote mode (`startCharge`/`stopCharge`, see `solax-api.md`), sent only when the place has **Разреши управлене** on (off by default); never add other control calls unless the owner asks.

### Inverter control: verified on the real inverter (2026-10-21, night, details in `solax-api.md` A2)

- **Push Power** (`push_power/positive_or_negative_mode`, `batteryPower` negative = charge) charges from the grid at the set power: 2000 W gave about 1.97 kW into the battery and a grid import of that plus the house load (4.75 kW = 2 + 2.75, seen in the SolaX app too); 500 W and 1500 W worked as well. The cap limits only the battery's share.
- **`timeOfDuration` ends the mode by itself** (`nextMotion` 160): back to `deviceStatus` 102 with no exit sent. `exit_vpp_mode` ends it at once; sent with nothing active it still answers `10000`/`status` 3.
- **A new command replaces the running one**, power and timer (500 W/900 s followed by 1500 W/300 s: the battery went to 1.48 kW and the mode ended at the second timer).
- **Delay:** the SolaX cloud data (and the app) show a command about 5 minutes late; readings only change every 5 minutes, so decisions work on stale values (the charge adds roughly 0.17 % per minute at 2 kW).
- Early exit at a target SOC works (the exit is the same call); in daytime Push Power wastes the panels' surplus, so charging is only planned in the night zone.

- **Charging efficiency:** on the night of 2026-10-28/29 (real 5-minute `solar_today`) the charge ran at about 1.95 kW and gained about 0.2 % per minute (about 2.05 kWh stored from about 2.9 kWh drawn, capacity 11.4 kWh), i.e. about 70 % of the charging power is stored. The per-place efficiency (measured, else default 85 %) is used in `InverterControl.timerSeconds`, `plannedChargeStart` and `PlannedCharge`: the battery gains power × efficiency, the grid supplies the full power; there is no extra margin. Too long a timer is harmless because the charge is ended as soon as the plan is reached. Short power dips (0-1.2 kW around 01:55 and 03:25) were seen when the command was re-sent; not investigated.
- **Euro figures include the losses:** the grid energy bought for `kwh` stored is `kwh ÷ efficiency`, so `nightCharge` cost = `kwh ÷ eff × night price` and saving = `kwh × day price − cost`; `missedCharge` lost = `kwh × day price − kwh ÷ eff × night price`. `NightCharge.efficiency` is sent to the dashboard (`nightLine`), which does the same arithmetic.

**Charge stops (`report/ChargeStops.kt`):** during the night charge the inverter gives way to the house. On the owner's inverter the charge runs at full power up to about 5.0 kW of house load, tapers to about 5.7 kW and is zero above it (15 nights, 2026-10-26..11-09, 875 charging slots), 3-5 times a night and 16 times on the coldest night (2026-11-08, 1.2 °C), so the battery stops short of 100 % (86 % on 11-07, 90 % on 11-08). The cause (owner's screenshots of the inverter's Advanced settings, 2026-11-09): **Main Breaker Limit 25 A** (5.75 kW per phase), Phase Unbalanced: Enable, Max Charging Current 30 A; the heat pump (about 5 kW) is **single-phase** and the connection is 15 kW for three phases, so the pump's phase has only 2-3 A left, the inverter spreads the charge over the three phases and cuts it to protect that phase. The API cannot read these settings and has no per-phase data; **nothing was changed in the inverter**. The app does not need the cause, only the behaviour, which it learns from the stored data, with no setting and no constant:
- **The load limit is measured:** `maxChargingLoad` takes the stored nights (`slotsByDay`: 5-minute `load_w` and `charge_w` of every finished day in `discharge_days`, 8-14 days; a night needs the day before it for the evening) and the highest house load at which the charge still went on (a slot charging at half of `max_charge_w` or more) is the limit: **5.60 kW** on 2026-10-26..11-09. Above it the charge pauses. Needs 3 nights that charged, else no limit and no stops are assumed (plain time). It is shown read-only in the settings as «Максимално ниво на зареждане: измерено 5,6kW» (`chargeLoadLimitW`, `measuredChargingLoadW`). It replaced a fixed 7 kW constant (load plus charge above 7 kW), which cut every slot above 5.0 kW completely and so overcounted the stops by about 3 slots a night.
- **The closest night is replayed:** `ChargeStops.slots` takes the stored night **closest by temperature** to the coming day's forecast minimum `tMin` (`minTemps`; the latest on a tie) and replays it backwards from the charge's end: a slot whose load is above the limit charges nothing. The stops follow the cold (the heat pump peaks more often), so the night with the nearest temperature is the best picture of the coming one. `STOP_SLOTS_PER_DEGREE` = 2 slots are added per degree that night was colder than the forecast (taken away when warmer, never below the plain time): the closest night cannot say more than it had (on 11-08, 1.2 °C, the closest planned night had 9 stopped slots against about 16 real). Without a forecast or temperatures the median night of all counts.
- **It feeds the start time, the timer and the chart:** the time the charge needs (`InverterControl.timerSeconds`, `latestStart`, `plannedChargeStart`) includes the stops, and the planned charge on the chart pauses in the replayed night's cut slots (`ChargeStops.cutSlots`, `PlannedCharge.cut`), so the line also shows when the battery is expected to be full.
- **Known limits:** the taper slots (5.0-5.7 kW) still charge a part of the power but are replayed as full charge (about one slot a night); the history holds finished days only, so at 22:00-23:59 the night that just ended in the morning (the most informative one) is not in it (its rows are in `solar_today` but are not used yet; on 2026-11-08 this cost the cold night 11-07 with 13 stopped slots); a night colder than all stored ones is planned like the coldest one plus the per-degree slots, so it can end a few points short; after a change of `max_charge_w` the limit follows within a week or two.
- **Why the closest night and not the median (2026-11-03, changed 2026-11-08):** with the second longest night the charge was full 50, 20 and 15 minutes before the night zone ended, and the house then ran on the battery in the cheap zone; the owner prefers ending a few percent short to a battery that sits full, so the plan follows a similar night, not the worst; a worse one ends short (the timer always runs to the end and the command is not re-sent).

**Automatic efficiency (`report/ChargeEfficiency.kt`):** after each `DischargeHistory` pass, `measuredChargeEffPct` takes the stored 5-minute `soc`/`charge_w` of the last days and, over consecutive steps in the night zone where both charge at >= 300 W and the charge is below 99 %, divides the energy stored (gain % x battery kWh) by the energy drawn (mean power x 5 min). It needs >= 1 kWh of such charging, is clamped to 30-100 % and stored in `locations.charge_eff_measured` (an earlier value stays when the days have no charging; wiped with the plant history). The solar charge in the day zone is not used.

### State of the night charge (2026-10-31)

Implemented and covered by tests, **not yet run on the real inverter** (checked only by replaying stored loads of 12 nights from the server database):

- **Charge time** = missing energy ÷ (`max_charge_w` × efficiency), made longer by the stops of the closest night by temperature (`ChargeStops`, measured load limit) + 60 s; efficiency = measured, else 85 % (no setting any more).
- **End:** 5 minutes before the day zone (`CHARGE_END_BEFORE_MS`); there is no other buffer. **Start:** the last 5-minute reading (fast window, not the 30-minute night interval) before the latest start (`end - need`) sends Push Power; a later reading starts late (the timer still runs to the end).
- **Readings:** 30 minutes at night, 5 minutes in the 30 minutes before the latest start (`night_plans.charge_from`) and before the charge end (`charge_until`), hourly by day (`batterySlot`, `batteryLoop` every 5 minutes). The bug that kept successful readings hourly (`battery_try_at`) is fixed, so the call count rose (see Call budget).
- **Why it was built:** on 2026-10-31 the charge started at 00:05 and stopped at 96 %: four times the house load rose and the charge fell to 0-1.4 kW (the battery was not discharged meanwhile; the grid itself reached 10 kW on other days without charging, so the stops are not the connection's limit). The cause is the inverter's per-phase protection (see Charge stops above): Main Breaker Limit 25 A, a single-phase heat pump, a 15 kW connection. A 25 A setting is already at or above what one phase carries and cannot be raised without risking the breaker, so the stops are structural. Open: whether grid charging can avoid the loaded phase (SolaX support or the installer), not known.

Expected from the replay (to check against the real nights): start at the 23:30 reading, battery full 15-40 minutes before the end, 100 % on every night. Unverified: the 5-minute reading window around the timer end on quiet nights (the battery is full before the window starts), what the inverter does at 100 % in Push Power. Not worth testing: the other remote modes (PV&BAT Individual, Power Control, SOC/Electric Quantity Target, Self-Consume) either serve the panels, which produce nothing at night, or do not set the battery power; none of them names an import limit, so Push Power stays the mode.

## Call budget (keep it small)

Every outside call counts against a quota (Open-Meteo weights calls by variables and days; SolaX has a call allowance), so **never add polling, and store every fetched value in the database**. Current cost per place and day: Open-Meteo 24 refreshes x 2 requests (daily values with `past_days` only when past days are missing, plus the 15-minute series); SolaX about 4-5 calls (statistics for the new day, battery charge about 40 times (hourly by day, every 30 minutes at night, every 5 minutes in the half hour before the charge's latest start and end), two history requests for the new day, plant record weekly). Place searches are cached in `geocode_cache` for 30 days. Rules that save calls: past days are stored once and never refetched; days with no data are marked done (`produced_through`, `battery_days_through`) rather than retried; credential changes for the same plant keep stored data (`configure`), a different account wipes it (`wipePlantHistory`); failures back off by cause (`SolaxError.retryMs`: 1 h ordinary/rate limit, 6 h allowance used up, 12 h wrong credentials/no access; `due_at`, `battery_try_at`, `history_try_at` hold the earliest next attempt) and changing the credentials resets the wait.

## Logging

- Code logs through kotlin-logging (`private val log = KotlinLogging.logger {}`, lazy messages `log.info { ... }`); logback (`src/main/resources/logback.xml`) writes `[thread] LEVEL logger - message` to stderr, `Exposed` only errors (it warns at every start about H2's auto-named foreign-key indexes), everything else from INFO.
- On the server systemd sends stdout and stderr to journald (`journalctl -u ilios`, `-f` to follow, `-p warning` for warnings and errors). Each line starts with the systemd priority prefix (`<3>` error, `<4>` warning, `<6>` info, `<7>` debug; `SyslogPriority`), added only when systemd has set `JOURNAL_STREAM`, so a terminal shows plain lines. kotlin-logging's own start-up line is switched off in the start script (`applicationDefaultJvmArgs`), because it would have no priority.
- What is logged: start-up and the database (opened, compacted from-to MB, failed), every SolaX failure (`SolaxGuard.attempt`: place and message or class name), each charge command (`SolaxService.startCharge/stopCharge` at INFO, failures at WARN in `InverterControl`), one INFO line per night-plan check, loop errors at ERROR, Open-Meteo refresh failures at WARN, the password-reset link when SMTP is not configured.
- **Never log credentials, tokens or secrets** (the SolaX secret, session tokens, passwords); the one exception is the documented fallback of printing the reset link when SMTP is not configured: unexpected exceptions are logged by class name only, only `SolaxError` messages (made to be shown) are logged in full. `LogbackConfigTest` loads the real `logback.xml` and fails on any logback warning.

## Never run the app on a copy of the real database with live credentials

The real `data/ilios.mv.db` holds the owner's SolaX Client ID/Secret. Starting the app on a copy of it starts the sync loop, which **makes real SolaX calls and spends the owner's quota**. For migration or UI checks first neutralise the copy (`UPDATE SOLAX SET CLIENT_ID='fake', CLIENT_SECRET='fake', TOKEN=NULL, TOKEN_EXPIRES=0`) and start with `SOLAX_URL=http://127.0.0.1:1`. Read-only inspection with the H2 shell is fine, but never select `client_secret` or `token`.

## Report and charts

- `GET /api/report` returns per place: `today`, `days` (21 days: previous, current, next week, Monday–Sunday), `watering` advice, `battery` (only `batteryKwh`, null when the place has no solar), `intraday` (today's 15-minute points with an `event`: thunder/snow/rain/wind/cloud).
- Battery recommendation line (`nightLine` in `dashboard.js`, fed by `report.night` = `nightCharge()` and `report.missed` = `missedCharge()`): tonight's kWh, its cost and its saving against the day price (`TARIFFS`, per supplier). "днес пропуснахте" counts only the day zone from its start: grid import (`TodayPoint.gridW`, 5-minute steps, positive = import) while the battery was at the reserved level + 1 %, **replayed against a battery that began the day zone fuller by its whole room** (`coverableImport`: that extra energy covers the import of the empty steps and is used up doing so; when the sun charges the real battery so far that the fuller one would overflow, the excess is lost; so the figure never exceeds the room at the day zone's start, e.g. 89 % of 11.3 kWh is 1.2 kWh, and is 0 when the sun filled the battery anyway) × (day − night price ÷ efficiency). A battery that never ran empty gives "днес няма спестявания"; before the day zone starts there is no figure.
- Solar kWh in `days[].kwh` is an **estimate from radiation** (`kWp × MJ/m² ÷ 3.6 × efficiency`, where the efficiency is **not a setting**: `calibratedRatio()` in `report/Solar.kt` derives it from past days that have SolaX production and stored radiation, needs ≥3 usable days, is clamped to 0.3–1.0 and falls back to 0.75); `days[].produced` is SolaX's measured value when the place is connected and is preferred for past days.
- Watering advice (plants/grass/trees, rule of thumb constants in `report/Watering.kt`) is shown as small chips in each place's collapsed summary row.
- Charts in `charts.js` are hand-written SVG strings. The weekly chart deliberately uses two y-axes (temperature, rain) to match the owner's reference image, with both axes labelled; the dataviz guidance would normally avoid that. Icon rows above the plots use the same outline style.
- The two day charts, **Времето** and **Батерия**, show 24 hours: **Батерия** shows a fixed window (see below), **Времето** 3 h back and 21 h ahead (`winStart(now, back)` in `charts.js`). Yesterday's and tomorrow's weather are stitched in: `intraday.prev/next` (Open-Meteo rows of yesterday are kept, only fetched days are replaced), and the battery chart's tomorrow part comes from `report.pvForecastNext`. The estimate (dashed charge line, grid bars) runs the 12 hours ahead too: `estimateDay(untilSlot = now + 144 slots)` goes past midnight with tomorrow's consumption pattern and `pvForecastNext`, its times wrap (the chart counts the wraps), and its summary figures (`peakSoc`, `importKwh`, `chargeNeeded`) still cover today only. With **Разреши управлене** on and a stored, not yet reached night plan, the estimate includes the planned grid charging (`PlannedCharge`, start from `plannedChargeStart` the way `controlInverter` times it: as late as possible to end 5 minutes before the day zone, or at once when a charge runs): the battery rises at `max_charge_w` up to the plan's target, is not discharged meanwhile and the grid supplies the charge plus the house (`EstimatePoint.chargeW`, shown in the tooltip); in the slots where the replayed past night's charge was cut for the house load (`PlannedCharge.cut`, from `ChargeStops.cutSlots`, the same night the time is worked out from) the battery stays flat, the grid serves the house and the tooltip says «зареждането е спряно – голяма консумация» (`EstimatePoint.cut`). Without a stored plan (the planner acts only once the battery is at its minimum) the report projects the plan the planner would make (`compensation()` + `nightTargetSoc()` on tomorrow's pattern and forecast) when the plain estimate drops to the reserved level + 1 % before the day zone, so the chart already shows the climb.
- The **Батерия** chart's window is 26 hours and always holds a whole night (`batteryWindow`): until 07:00 it runs from 05:00 yesterday to 07:00 today (the night in progress is visible), from 07:00 on from 05:00 today to 07:00 tomorrow (`batteryChart`, split into `batterySeries`, `batteryGeometry` and the drawing helpers; 3-hour ticks, the date under each midnight inside the window, the "now" line inside it, the estimate only as far as it runs, 12 h ahead). Yesterday's points come from `report.batteryPrev` (`solar_today` keeps yesterday's rows).
- Keep chart markup free of user text (names are never put into the SVG strings).

## Gotchas learned

- Exposed 1.x packages are `org.jetbrains.exposed.v1.core.*` and `org.jetbrains.exposed.v1.jdbc.*`.
- `SchemaUtils.createMissingTablesAndColumns` adds columns/tables but **never drops** columns. `Daily.fetchedAt` is `NOT NULL` without a default, so it must stay in the table definition even if unused.
- Column `day` is an H2 keyword: Exposed quotes it as lowercase `"day"`. In the H2 shell use `SELECT "day" …`; other columns are unquoted/uppercase.
- Inside `MimeMessage.apply { }` identifiers like `from`/`sender` resolve to the message's properties – hence `mailFrom`.
- The H2 file is locked while the app runs; copy `data/ilios.mv.db` to inspect it.
- H2 never gives back the space of deleted rows: the prod file was 17.9 MB for 0.27 MB of data (every rewrite of today's rows and the hourly weather replacement leave dead pages; closing normally or `MAX_COMPACT_TIME` reclaimed almost nothing, only `SHUTDOWN COMPACT` did). So `initDb` runs `SHUTDOWN COMPACT` on an existing file through a plain JDBC connection **before** it opens the database (`compact` in `Database.kt`, so before anything else of the app starts; a failure is logged and the start goes on). The file therefore shrinks at every restart and grows between them (about 0.8 MB a day).
- Open-Meteo geocoding is called with `language=bg`; the search UI needs the Търси button (no search-as-you-type yet).
